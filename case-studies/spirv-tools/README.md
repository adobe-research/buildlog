# Case study: building SPIRV-Tools with buildlog

SPIRV-Tools generates its opcode, operand and extended-instruction tables
at build time. Python scripts (`utils/ggt.py` and others) read the JSON
grammars that **SPIRV-Headers** ships. SPIRV-Headers is a separate package,
so the version of that imported data determines the generated code. In
Halide, the generators' inputs were in the source tree. This study imports
SPIRV-Headers as an installed package and reads its grammar files as data
files of that package. It then runs the generators with the user's Python,
and builds the core libraries, the optimizer, four tools and four unit-test
programs. It compares the result with SPIRV-Tools' own CMake build on this
Mac, and shows that `buildlog why` traces a generated table's input to the
package location the user chose. It also models a few of SPIRV-Tools'
boolean options, with `-Werror` as the user's decision only.

## Running

```sh
case-studies/spirv-tools/baseline/run-cmake.sh          # the CMake baseline (~5 min)
P=case-studies/spirv-tools/project/presets
uv run --frozen buildlog configure \
  --user $P/apple-clang-arm64.toml --user $P/homebrew-python.toml \
  --user $P/spirv-headers-prefix.toml --user $P/homebrew-googletest.toml \
  -D SPIRV_HEADERS_PREFIX=$SPIRV_HEADERS_PREFIX \
  -C build/case-spirv-tools/bl/release case-studies/spirv-tools/project
ninja -C build/case-spirv-tools/bl/release/souffle -j4
uv run --frozen buildlog test -C build/case-spirv-tools/bl/release case-studies/spirv-tools/project
uv run --frozen pytest -q -n 4 tests/test_spirv_tools_case.py
```

Add `--user $P/werror.toml` for warnings as errors, or replace the
googletest preset with `$P/skip-tests.toml` when googletest is absent.

## Ledger

The acceptance tests are in `tests/test_spirv_tools_case.py` (13 tests,
about 45 s with `-n 4`). They configure, generate the tables, build three
tools and one test program, and check the claims below that do not need a
full build. The full-build comparisons were run by hand (the commands are
below).

### Phase 1: the CMake baseline

`baseline/run-cmake.sh` checks the pin and a clean tree, then configures,
builds (986 edges, about 5 minutes at `-j4`) and runs ctest (**24/24
passed**). It writes the normalized files listed above.

**How upstream finds SPIRV-Headers.** It has no `find_package` path.
`external/CMakeLists.txt` uses `SPIRV-Headers_SOURCE_DIR` if it is set,
and otherwise `add_subdirectory(external/spirv-headers)`.
`SPIRV_HEADER_INCLUDE_DIR` is `<dir>/include`, and the grammars are read at
`${SPIRV_HEADER_INCLUDE_DIR}/spirv/unified1/*.json` (plus
`spirv/spir-v.xml`). The baseline gives it the *install prefix* as the
"source dir". This works only because the installed `include/` has the
same layout as the source tree's. It is the nearest upstream comes to
"imported as an installed package"; see #6405 in the design input.

**Generator commands** (`baseline/generators.txt`). All five run as
`cd $BUILD/source && /opt/homebrew/bin/python3 $SRC/utils/<script> ...`:

- `ggt.py` writes `core_tables_body.inc` and `core_tables_header.inc` from
  the core grammar and 15 extended-instruction grammars;
- `generate_registry_tables.py` writes `generators.inc` from `spir-v.xml`;
- `generate_language_headers.py`, run twice, writes `DebugInfo.h` and
  `OpenCLDebugInfo100.h`;
- `update_build_version.py` writes `build-version.inc` from `CHANGES`, and
  also runs `git describe` in the checkout, an input neither build declares.

**The RTTI quirk (upstream).** `spvtools_default_compile_options` calls
`add_compile_options(-fno-rtti)` inside a per-target function. That is
directory scope, so it reaches the targets defined *after* the first call
in each directory, not the first one. As a result, SPIRV-Tools-shared,
SPIRV-Tools-opt and test_spirv_unit_tests are built with RTTI, and
SPIRV-Tools-static, the tools and the other tests without. The spec states
the option's intent instead: `ENABLE_RTTI=off` means `-fno-rtti` for every
target.

### Phase 2: SPIRV-Headers as an imported package

**How it is stated.**
- The user names the prefix (`presets/spirv-headers-prefix.toml`,
  `package_prefix = [["${SPIRV_HEADERS_PREFIX}"]]`).
- buildlog-cpp's cmake provider finds and imports SPIRV-Headers' shipped
  CMake export, `share/cmake/SPIRV-Headers/SPIRV-HeadersConfig.cmake`. That
  file is an `install(EXPORT)` targets file named as a Config file. It gives
  the INTERFACE target `SPIRV-Headers::SPIRV-Headers` with
  `INTERFACE_INCLUDE_DIRECTORIES ${_IMPORT_PREFIX}/include`.
- I wrote no CPS for SPIRV-Headers.

**Grammar files as package data files** (`rules.dl`, "Data files of an
imported package"; `generators.toml`).
- `package_data(key, target, rel)` states one file below the include dir
  that the imported target states. There are 17 rows: the core grammar, 15
  extended-instruction grammars and `spir-v.xml`.
- `package_data_file(c, key, path)` joins that with the import's `eff_prop`
  include dir, and requires `import_origin`, so the file must be a fact
  about an import.
- It is an error if the package states no include dir or several, or if a
  generator's data file is missing.

This is upstream's own derivation (`${SPIRV_HEADER_INCLUDE_DIR}/spirv/...`).
It is a workaround, because buildlog has no notion of a package's data
files (design input D1).

**Matches.** The grammar arguments are the files in the user's prefix, and
they are explicit inputs of the generator edges. Touching
`extinst.debuginfo.grammar.json` in the prefix reruns exactly the two
generators that read it (`ggt.py` and the DebugInfo header).

**Differs.** The include dir reaches SPIRV-Tools' compiles as `-isystem`
(buildlog's policy for a dependency's dirs), where CMake uses `-I`.

### Phase 3: the generators and the interpreter

(UX pass, 2026-09-30: the five generators are now core's generator vocabulary,
`[generator.X] run = ["python3", "${src:utils/ggt.py}", "--spirv-core-grammar=${pkg:core}",
"--core-tables-body-output=${out:core_tables_body.inc}", ...]`, with `owner` and `label` in
`[defaults.generator]`; `package_data` and `gen_user` moved to core, and the ~80 lines of
`pygen`/`package_data`/`gen_user` rules left rules.dl. The graph is identical. The text below
describes the original shape.)

**How it is stated.** `pygen(g, owner, script)` is an action of the owner,
`spirv-tools-tables`, and runs `pygen_interpreter(owner, tool)`. Its ranked
arguments are:

- `pygen_arg`: a literal;
- `pygen_src`: a source file, which is also an input;
- `pygen_data`: a package data file, which is also an input;
- `pygen_out`: an output in `out:gen/<config>/<owner>/`.

The ranks follow upstream's argv. `gen_user(t, owner)` gives t the
generated dir as a private include dir (upstream: PRIVATE
`${spirv-tools_BINARY_DIR}`). It also makes t's compiles wait for the
generated headers (upstream: `add_dependencies`). The pattern is Halide's
flatc action, generalized to an interpreter plus a script.

**The interpreter.** `tool = "python3"` is a target reference the author
writes. The user binds it (`presets/homebrew-python.toml`): a CPS that the
user ships (`presets/Python3.cps`, one executable component `Interpreter`
at `/opt/homebrew/bin/python3`) and `alias python3 -> Python3:Interpreter`.
The CPS file must be named after the package (`Python3.cps`); my first
name, `homebrew-python3.cps`, was rejected (*package 'Python3' is not named
like its file*). buildlog has no program discovery, so this is a workaround
(design input D4).

**Matches.**
- All six generated files are **byte-identical** to the baseline
  (`test_generated_tables_match_the_baseline`).
- The five generator commands equal the baseline's when the paths are
  normalized (`test_generator_commands_are_upstreams`).

**Differs.**
- buildlog runs the generators from the Ninja dir with paths relative to
  it. CMake runs them `cd $BUILD/source` with absolute paths.
- `build-version.inc` depends on `git describe`, as upstream's does, and
  neither build declares that input (D6).

### Phase 4: the libraries, the optimizer and the tools

**How it is stated.**
- `SPIRV-Tools` (79 files, `sources.toml`) is one `library` with
  `default_linkage = "both"`, as upstream builds `SPIRV-Tools-static`
  (output name `SPIRV-Tools`) and `SPIRV-Tools-shared` from one source
  list. Core builds two instances: `SPIRV-Tools` (static,
  `libSPIRV-Tools.a`) and `SPIRV-Tools@shared`, whose file is named by
  `linkage_output_name` (`libSPIRV-Tools-shared.dylib`). The shared build
  adds `SPIRV_TOOLS_IMPLEMENTATION`, the public `SPIRV_TOOLS_SHAREDLIB` and
  `-fvisibility=hidden` (`linkage_prop`). Until step 4 these were two
  targets from a library-variant template.
- `SPIRV-Tools-opt` (120 files) requires static linkage, with upstream's
  reason (`linkage = { require = "static", why = ... }`); it links the
  SPIRV-Tools instance of its own linkage. The tools and tests pin the
  static library (`dep_linkage`), `test_c_interface_shared` the shared one.
- The tools are `spirv-as`, `spirv-dis`, `spirv-val` and `spirv-opt`.
- `spvtools_target` gives every target `spvtools_default_compile_options`,
  stated once in `spec.toml`: the warnings, `-ftemplate-depth=1024`,
  `-Wextra-semi`, C++17, PIC, no exceptions, and no RTTI unless
  ENABLE_RTTI.

The buildlog build has 304 edges without the tests and 335 with them. It
took 71 s at `-j4`, against about 5 minutes for CMake's 986 edges, which
include googletest, effcee, re2, abseil and 24 test programs. A fresh
configure took 17 s.

**Matches the baseline** (checked by hand with `nm`, `ar t`, `otool` and
the compile lines; the static library's flags are also a test).
- Every in-scope target compiles the same number of objects: 79, 79, 120,
  3, 3, 4, 4, 74, 1, 1 and 1.
- For the static library (CMake's SPIRV-Tools-static), the `-D`, `-W`, `-f`, `-O` and `-std` flags are
  the same set as CMake's, apart from `-Werror`
  (`test_static_library_flags_match_the_baseline`).
- `libSPIRV-Tools-shared.dylib` has the same 79 exported symbols, the same
  install name (`@rpath/libSPIRV-Tools-shared.dylib`, 0.0.0/0.0.0) and the
  same `otool -L` (libc++ and libSystem).
- `libSPIRV-Tools.a` has the same members and the same defined symbols.
- The tools have the same `otool -L`.
- **Smoke test.** The buildlog tools and the CMake tools give
  byte-identical results for assembling, validating, disassembling and
  `spirv-opt -O` + disassembling `smoke/sample.spvasm`, and both report
  `SPIRV-Tools v2026.3 v2026.3-0-gb707790a`. The test
  `test_tools_round_trip_a_module` checks this against `smoke/sample.dis`.

**Differs, and why.**
- **RTTI.** `libSPIRV-Tools-opt.a` has 2,656 more symbols in CMake's
  build. All of them are RTTI (`__ZTI`/`__ZTS` typeinfo, and
  `std::function`'s `target`/`target_type`). The cause is the upstream
  quirk above, which builds opt, the shared library and the unit tests
  without `-fno-rtti`. buildlog passes `-fno-rtti` everywhere.
- **`-fPIE` vs `-fPIC` on executables.** CMake spells
  `CMAKE_POSITION_INDEPENDENT_CODE` as `-fPIE` for executables. buildlog's
  `cc.pic=on` is `-fPIC` for every kind. On arm64 macOS all code is
  position-independent anyway (D8).
- **`-DSPIRV_Tools_shared_EXPORTS`.** CMake adds this define to every
  shared library; no source reads it.
- **`-Werror`.** Upstream's SPIRV_WERROR is on by default. Here it is the
  user's `cc_werror` (phase 7).
- **Target spelling, depfiles, archiving, paths.** These are the same as
  in zlib's ledger (`--target=arm64-apple-macos13 -isysroot <SDK>` vs
  `-arch arm64`, `ar rcs`, `obj/<cfg>/<target>/`).
- **Flag order.** buildlog emits a target's compile flags as a lexically
  sorted set, and upstream's order is not kept. This matters only for
  order-dependent pairs (phase 6, D5).

**Shared-library versioning (recorded, not modelled).**
- `SPIRV-Tools-shared` has **no `VERSION` and no `SOVERSION`**
  (`source/CMakeLists.txt` sets neither, and `project(spirv-tools)` has no
  VERSION).
- On macOS the dylib is `libSPIRV-Tools-shared.dylib` with install name
  `@rpath/libSPIRV-Tools-shared.dylib`, **compatibility version 0.0.0,
  current version 0.0.0**, and no versioned symlinks. The buildlog build
  gives the same, because buildlog does not model these either.
  Homebrew's 1.4.357.0 keg also ships 0.0.0/0.0.0.
- The only version upstream exports is in pkg-config:
  `SPIRV-Tools-shared.pc` says `Version: 2026.3.1`, from `CHANGES`'s first
  line plus ".1" (`cmake/write_pkg_config.cmake:30`).
- The CMake export (`SPIRV-ToolsTarget.cmake`, installed with a `SPIRV-ToolsConfig.cmake`
  that `source/CMakeLists.txt:406` writes with `file(WRITE)`) has no `ConfigVersion.cmake`, so
  `find_package(SPIRV-Tools 2026.3)` cannot check a version.
- The static `SPIRV-Tools` archive and `SPIRV-Tools-opt` are static and
  have no ABI version.

### Phase 5: provenance and the version switch

**The headline.** Take the `--spirv-core-grammar=` argument of the edge
that writes `core_tables_body.inc`, and ask `why` (`--leaves`):

```
buildlog why -C <build> --leaves \
  --flag "--spirv-core-grammar=$PREFIX/include/spirv/unified1/spirv.core.grammar.json" \
  --output gen/arm64-macos.release.none/spirv-tools-tables/core_tables_body.inc \
  case-studies/spirv-tools/project
```

The proof reaches these leaves:

- `gen_word("core_tables", 4000, "--spirv-core-grammar=", "pkgkey", "core", "")` ←
  the `run` line of `[generator.core_tables]` in `generators.toml` (before the UX pass,
  `pygen_data("core_tables", 2, "--spirv-core-grammar=", "core")`);
- `package_data("core", "SPIRV-Headers::SPIRV-Headers",
  "spirv/unified1/spirv.core.grammar.json")` ← `generators.toml:11`;
- `res_pkg_prop(..., "cc.include_dir", "$PREFIX/include")` ←
  `$PREFIX/share/cmake/SPIRV-Headers/SPIRV-HeadersConfig.cmake:62`, and
  `res_pkg_target(...)` ← `SPIRV-HeadersConfig.cmake:59`;
- `res_pkg_find(... "prefix", "$PREFIX" ...)`, `package_provider("cmake")`
  ← buildlog-cpp's manifest;
- `package_prefix("$PREFIX")` ← `presets/spirv-headers-prefix.toml:4`,
  **the user's line**.

The full proof also shows `import_origin("SPIRV-Headers::SPIRV-Headers",
"arm64-macos", "cmake", "prefix", "$PREFIX")`. The interpreter traces to
`alias("python3", "Python3:Interpreter")` ←
`presets/homebrew-python.toml:5`, `package_file(...)` ← line 4, and
`Python3.cps:6`. `test_why_a_grammar_input_leads_to_the_users_prefix` and
`test_the_interpreter_is_the_users` check both.

**What `why` cannot say: the version.** The chain names the location, not
"SPIRV-Headers 1.4.357.0".
- SPIRV-Headers' metadata does not know its release. The project's
  `VERSION` is 1.5.5 in every release, so `SPIRV-HeadersConfigVersion.cmake`
  and `SPIRV-Headers.pc` both say 1.5.5 for vulkan-sdk-1.4.357.0 and
  1.4.363.0 alike.
- buildlog's CMake importer reads no version files anyway.
- Only the Homebrew keg's realpath (`Cellar/spirv-headers/1.4.357.0`)
  carries the version, and the preset names the `opt/` symlink.

The data identifies itself only by content (D2).

**The version switch.** `-D SPIRV_HEADERS_PREFIX=.../prefix-alt`
(vulkan-sdk-1.4.363.0), reconfigured in the same build dir:
- The four grammar-driven generators rerun, and `build_version` does not.
  All compiles rerun too, because the `-isystem` dir changed.
- `core_tables_body.inc`, `core_tables_header.inc` and `generators.inc`
  change. `DebugInfo.h` and `OpenCLDebugInfo100.h` don't, because those two
  grammars are identical in the two releases.
- The build succeeds.
- The six files are **byte-identical to CMake's** on the same prefix
  (`cmake-build-alt`, `-DSPIRV-Headers_SOURCE_DIR=.../prefix-alt`).
- `why` then leads to `package_prefix(".../prefix-alt")`.

`test_another_spirv_headers_changes_the_tables` checks this; it skips
without the second install.

**The location switch.** `presets/homebrew-spirv-headers.toml` (the
Homebrew keg, the same release) gives generated files byte-identical to
the baseline, with arguments under `/opt/homebrew/opt/spirv-headers/`.

**Incremental.** Touching one grammar reruns the generators that read it.
Both builds then recompile everything that includes the tables (324 edges
here), because the scripts rewrite their outputs unconditionally. CMake's
`restat = 1` does not help it for the same reason.

### Phase 6: tests

**How they are stated** (`tests.toml`). There are four of upstream's
`add_spvtools_unittest` programs that need only googletest (no effcee):
`test_spirv_unit_tests` (74 sources: the assembler, disassembler, binary
parser, text-to-binary and friends), `test_c_interface`,
`test_c_interface_shared` (against the dylib) and `test_cpp_interface`
(against opt).
- They depend on `GTest::gmock_main`, imported from Homebrew googletest's
  CMake export (`presets/homebrew-googletest.toml`).
- googletest's targets link `Threads::Threads`, which CMake's FindThreads
  defines. Nothing in buildlog defines it, so `tests.toml` declares it as
  an empty interface target (D7).
- The tests' `-Wno-undef -Wno-shadow` after `-Wundef -Wshadow` is stated
  as `spvtools_flag_off` (D5).
- The `test` facts use ctest's names (`spirv-tools-test_*`).

**Result.** `buildlog test` gives **4 passed**. Each program runs the same
number of gtest cases as CMake's, and all pass: 6416, 10, 10 and 22.
`test_c_interface_tests_pass` runs `buildlog test -R c_interface$`.

**Differs.**
- googletest is Homebrew's 1.18.0, not DEPS' `8240fa7d` built from
  `external/`.
- Homebrew's static gtest was built for macOS 26, and buildlog links for
  macOS 13. ld warns *object file ... was built for newer 'macOS' version
  (26.0) than being linked (13.0)*. A package's deployment target is not a
  fact buildlog checks (D10).
- The 20 other ctest programs (opt, val, link, reduce, diff, the tools'
  tests, ...) are not modelled. Most need effcee/re2/abseil, which are
  source-only in DEPS and not installed on this Mac.
- The tests see `SPIRV-Tools/include` as `-isystem` (a dependency's public
  dir). CMake uses `-I`.
- Without googletest and without SPIRV_SKIP_TESTS, configure fails with
  *unresolved dependency: GTest::gmock_main*. Upstream silently skips the
  tests when `gmock_main` is not a target. Here the user must say
  `skip-tests`, which I think is the better behaviour.

### Phase 7: options

**How they are stated** (`spec.toml`).
- `option_decl` declares six options with upstream's defaults:
  SPIRV_SKIP_EXECUTABLES off, SPIRV_SKIP_TESTS off, SPIRV_COLOR_TERMINAL
  on, SPIRV_LOG_DEBUG off, ENABLE_RTTI off and SPIRV_BUILD_FUZZER off.
- Conditions over `option.<name>` gate `prop_when`s: the two defines and
  `cxx.rtti=off`.
- **What is built.** A request cannot depend on an option:
  `request(t, n) :- ..., !spvtools_skipped(c, k)` is rejected with
  *request depends on needed, creating a negation/stratification cycle*
  (`src/buildlog/layers.py:1131`). So rules.dl requests one aggregate,
  `spvtools-all` (CMake's `all`), whose `dep_when` edges to the tools and
  tests carry the conditions `build_executables` and `build_tests` (D3).
- **SPIRV_BUILD_FUZZER=on is an error.** It would need protobuf, libFuzzer
  and spirv-fuzz, which are out of scope, so turning it on fails loudly
  instead of being ignored.

**Checked.**
- `skip-executables`: 287 edges, no programs, the three libraries.
- `skip-tests`: the libraries and tools, no googletest needed.
- `no-color-rtti`: neither `-DSPIRV_COLOR_TERMINAL` nor `-fno-rtti`.
- `fuzzer`: *option not supported by this spec: SPIRV_BUILD_FUZZER=on*.

Tests: `test_skip_executables_builds_the_libraries_only` and
`test_the_fuzzer_is_rejected`.

**-Werror (SPIRV_WERROR).** Under buildlog's policy, `-Werror` is the
user's opt-in, so SPIRV_WERROR is not an option.
- `presets/werror.toml` (`cc_werror = [["release", "*"]]`) puts `-Werror`
  on all 369 compiles, and the full build succeeds with Apple clang 21.
- Without it there is no `-Werror`.
- If the author puts `-Werror` in `spvtools_flag`, configure fails with
  *-Werror is a user decision: SPIRV-Tools: -Werror (cxx compiler
  apple-clang is the user's choice ...)*
  (`plugins/buildlog-cpp/src/buildlog_cpp/layers/L4_cxx.dl:323`).

Tests: `test_werror_is_the_users_opt_in` and
`test_an_author_werror_is_rejected`.

**Not modelled.** SPIRV_BUILD_COMPRESSION
(upstream's FATAL_ERROR: the codec was removed), SPIRV_TOOLS_BUILD_STATIC (fixed at upstream's
default ON: SPIRV-Tools-opt is static), SPIRV_BUILD_LIBFUZZER_TARGETS,
SPIRV_WARN_EVERYTHING, SPIRV_CHECK_CONTEXT (debug builds),
SKIP_SPIRV_TOOLS_INSTALL and ENABLE_EXCEPTIONS_ON_MSVC.

## Design input

Ranked by importance for the design step.

**D1. An imported package's data files are not a concept.** In buildlog's
terms, SPIRV-Headers' grammar JSON files are data files of an imported
package.
- *The rule I wanted:* `pygen_data(g, r, "--spirv-core-grammar=",
  pkg_file("SPIRV-Headers::SPIRV-Headers", "spirv/unified1/spirv.core.grammar.json"))`,
  with core resolving the path from the import. The package itself could
  say where its data lives (CPS has no component for data files; CMake
  packages set variables such as `SPIRV_HEADERS_GRAMMAR_DIR` by
  convention).
- *The rule I wrote* (`rules.dl`, "Data files of an imported package"):
  `package_data_file(c, k, cat(d, "/", r)) :- package_data(k, h, r),
  eff_prop(h, c, "cc.include_dir", d, _), import_origin(h, p, _, _, _),
  config_platform(c, p)`.

  It uses a C++ usage requirement (the include dir) as the package's data
  root. It works only because SPIRV-Headers has exactly one include dir and
  ships its data below it. The alternative, `import_origin`'s root plus
  `include/`, would hard-code a layout.
- *A principled fix* has two parts:
  - core exports the imported package's root, meaning the package's prefix
    (CMake's `_IMPORT_PREFIX`, CPS's `@prefix@`), which is not the search
    root `import_origin` gives;
  - core adds a relation for files within it (`import_file(t, rel, path)`),
    so that generators, `configure_file` and install rules can depend on
    package data with the same provenance as a property.

  This belongs in `L3_discovery.dl` next to `import_origin`, with importers
  reporting the prefix (cmake_export.py already computes `_IMPORT_PREFIX`).
- *Upstream relevance:* SPIRV-Tools itself cannot consume an installed
  SPIRV-Headers except by the SOURCE_DIR-as-prefix trick (phase 1).
  #6405 ("build is confused by installed SPIRV-Tools") is the same
  ambiguity between the vendored and the installed package. In buildlog
  the user's `package_prefix` decides, and `why` shows it.

**D2. Package versions and data identity.** `why` shows the location, but
not "SPIRV-Headers 1.4.357.0".
- The CMake importer skips `<Pkg>ConfigVersion.cmake` (cmake_export.py's
  docstring, line 36), and only the LLVM plugin reports `package_version`
  (`L3_discovery.dl:361`).
- Even if it read the file, SPIRV-Headers' metadata says 1.5.5 in every
  release, so the metadata version cannot identify the grammar data.
- Two fixes:
  - importers report the metadata version as a fact (D2a);
  - buildlog records a content digest of every package data file it reads
    (D2b), so that `why` can say "spirv.core.grammar.json (sha256 …) of
    SPIRV-Headers found at <prefix> because presets/…:4". A user pin such
    as `package_expect(t, digest|version)` then turns an unexpected
    upgrade into a configure error instead of different tables.
- **Symlinked prefixes.** Homebrew's `opt/spirv-headers` is a symlink, so
  a keg upgrade changes the data without changing any path buildlog sees.
  Only the files' mtimes trigger a rebuild. A digest would make that
  robust, and recording the realpath (`Cellar/.../1.4.357.0`) in
  `import_origin` would show the version in `why`.

**D3. Requests cannot be gated on options.**
- *The rule I wanted:* `request(t, n) :- spvtools_request(t, k),
  config_decl(n, _), !option_skips(k)`, reading `option_value` directly.
- *What happens:* `request` must not depend on anything that reaches
  `needed`, and `config_attr` does. The composed program is rejected
  (`src/buildlog/layers.py:1131`).
- *The workaround:* an aggregate target `spvtools-all` with
  condition-gated `dep_when` edges (`rules.dl`, "Options that decide what
  is built"). It works, but "what is built" becomes a dependency closure,
  and `buildlog why` on a missing tool has no request to point at.
- zlib hit the same wall. *A principled fix:* expose the options'
  build-wide values as a declaration-level relation
  (`option_effective(name, value)` from `option_decl`/`option_value`, not
  from `config_attr`), so that requests can read it without touching
  `needed`. It belongs in `L1_options.dl`.

**D4. No program discovery.** A generator's interpreter is a user
decision. The only way to bind it was a CPS the user writes for an
executable, plus an `alias`.
- The CPS must be named after its package (`Python3.cps`), and it records
  no Python version, so `why` shows the path but not "Python 3.14.7".
- *A principled fix:* a core user relation `program(ref, path)`, or a
  provider that probes `find_program`-style for a name on PATH with an
  optional version query. Either produces the same executable target with
  `import_origin` provenance. It belongs in core L3 plus a small importer.
- CMake's `Python3_EXECUTABLE` is the same decision, made implicitly.

**D5. Compile flags are a lexically sorted set.** `cxx.compile_flag`
(`L4_cxx.dl:124-130`) sorts a target's flags, so upstream's `-Wshadow …
-Wno-shadow` cannot be written; the later one would not reliably win.
- *The workaround:* `spvtools_flag_off(t, f)` states the net effect, so
  the tests get neither flag.
- *A principled fix:* either ranked flags (an author-visible order) or
  warning keys (`cc.warning(shadow)=off`) that the family spells as the
  last word. The second fits buildlog's typed-settings direction better.

**D6. Generators with undeclared inputs.** `update_build_version.py` runs
`git describe` in the checkout. Neither CMake nor buildlog declares
`.git/HEAD` or the tags as inputs, so `build-version.inc` goes stale on a
new commit until `CHANGES` changes. buildlog could make the version a
configure-time probe fact (git describe → a `pygen_arg`), which would also
make it visible to `why`.

**D7. `Threads::Threads` is undefined.** Every CMake package that uses
`find_dependency(Threads)` references it; googletest's export does. The
spec had to declare an empty interface target. *A principled fix:*
buildlog-cpp defines `Threads::Threads` per platform (nothing on Darwin,
`-pthread` on Linux), as a built-in import.

**D8. `-fPIE` has no spelling.** `cc.pic=on` gives `-fPIC` for every
target kind. CMake uses `-fPIE` for executables. A `family_pie_arg`
chosen by kind in `L4_cxx.dl` would match.

**D9. No `restat` on generator actions.** `action_restat` exists, but it
makes no difference for these scripts, which rewrite their outputs
unconditionally (in CMake too). A write-if-changed wrapper, like
`builtins.py`'s copy, would save the 322-compile cascade on a grammar
change that doesn't change the tables.

**D10. A package's deployment target is not checked.** Homebrew's gtest
objects are for macOS 26, and the build targets 13. ld warns; buildlog
doesn't know. Importers could report `LC_BUILD_VERSION` minos for
archives, and core could compare it with the configuration's platform.

**D11. Options are one flat namespace per build.** SPIRV-Tools' options
are already `SPIRV_`-prefixed, except `ENABLE_RTTI`. glslang also has an
`ENABLE_RTTI`. If both were built in one buildlog project, as upstream
does with add_subdirectory, the names would collide. Options namespaced by
their declaring package (`option.spirv-tools.ENABLE_RTTI`) would avoid
that.

**D12. Shared-library versions (not implemented, per the PI).** buildlog
does not model SOVERSION, VERSION or the Mach-O compatibility/current
version. For SPIRV-Tools this changes nothing today, because upstream sets
none: 0.0.0/0.0.0, no SONAME version, and every release is ABI-unversioned.
That is exactly the case where an exported version constraint matters,
though:
- The only version a consumer can see is pkg-config's `2026.3.1`, a
  release number with no ABI promise. The C API (`libspirv.h`) is meant to
  be stable, but the C++ API changes between releases.
- **CPS.** An export would state `version: "2026.3.1"`. It should state
  **no `compat_version`** (or `compat_version` equal to `version`), since
  upstream promises no compatibility between releases. The honest
  `export_compat` would then be "exact": a downstream
  `requires: {"SPIRV-Tools": {"version": "2026.3"}}` should match only
  that release, not "2026.3 or newer".
- If buildlog later models `native_version(t, version, compat)`, then a
  target with no version should mean install name without versions, as
  upstream's. The exported `compat_version` should come from the same
  author fact, not be guessed from `version`. With compat 0.0.0 on Mach-O,
  dyld accepts any replacement dylib; buildlog could warn when a package
  exports a shared library without a compat version.
- The dependency direction matters too. SPIRV-Tools' own generated code
  depends on the SPIRV-Headers *data version* (D2), so a SPIRV-Tools
  export's `requires` on SPIRV-Headers should be exact (the DEPS pin),
  whereas SPIRV-Headers' metadata says 1.5.5 for every release. A
  meaningful constraint needs D2's data identity first.

**What buildlog solves here.**
- The imported-vs-vendored ambiguity (#6405) becomes a user decision with
  provenance.
- `-Werror` stays out of the author's hands. #5904 ("2024.3 Build Failure
  with GCC 14") is a GCC array-bounds warning that upstream's default
  SPIRV_WERROR turned into a failed build.
- The RTTI quirk cannot happen, because a property is per target, not per
  directory.
- Missing googletest is an error, not a silent skip.

**What it doesn't solve.**
- Version identity of imported data (D2).
- The dual Bazel/GN build (#2810).

**U1. A generator is ~20 facts spread over five relations (Datalog + TOML).**

`pygen_interpreter` rows with hand-numbered ranks, plus ~45 lines of rules
(`rules.dl`, "Python generators") to turn them into
`action`/`action_arg`/`action_in`/`action_out`. ggt.py alone is 20 rows:

```toml
pygen_data = [
  ["core_tables", 2, "--spirv-core-grammar=", "core"],
  ["core_tables", 3, "--extinst=,", "glsl"],

]
```

What I wished for (about 8 lines, no rules):

```toml
[generator.core_tables]
owner = "spirv-tools-tables"
run = ["python3", "src:utils/ggt.py",

  "--core-tables-header-output=${out:core_tables_header.inc}",

  # ...
]
```

That is an argv with typed placeholders (out, src, package file), where
the rank is the position and inputs and outputs are inferred. Halide's flatc
rule would use the same table. Saving: ~130 lines of this study, ~45 of
them Datalog.

**U2. Package data files need a key indirection (17 rows × 2).** Every
grammar is named once in `package_data` (`["core",
"SPIRV-Headers::SPIRV-Headers", "spirv/unified1/spirv.core.grammar.json"]`,
which tombi then wraps to 5 lines when it is long: 71 lines for 17 rows)
and again by key in `pygen_data`. The package name is repeated 17 times.
Wished for: the inline `${pkg:...}` above, or one table per package
(`[package_data."SPIRV-Headers::SPIRV-Headers"] core = "spirv/..."`).
The ~12 lines of `package_data_file` rules are the D1 workaround.

**U3. Every target is listed in three or four lists.** Each target appears
in `spvtools_target`, `gen_user`, `spvtools_request` (and `test`, and
`spvtools_flag_off` twice for tests) as well as its own `[target.X]`
table: the 11 target names occur 68 times in `targets.toml` + `tests.toml`.
Wished for: a per-target key (`[target.spirv-as] traits = ["spvtools",
"uses-tables", "executable-request"]`), or a defaults table that applies
to every target in a file:

```toml
[defaults]               # every target in this file
spvtools = true
gen_user = "spirv-tools-tables"
```

Saving: ~35 lines.

**U4. Project-wide defaults need Datalog.** "Every SPIRV-Tools target gets
these flags and props" is three rules plus five `.decl`s (`rules.dl`
"spvtools_default_compile_options", 10 lines). This is CMake's
`spvtools_default_compile_options(target)`, and I expect every study to
write it. Wished for: a TOML `[profile.spvtools]` table of `prop` /
`prop_when` that targets opt into (`profile = "spvtools"`).

**U5. Options are stated three times.** An option is an `option_decl`, then
a named `condition` (`["no_rtti", "$Eq(option.ENABLE_RTTI, off)"]`), then
a `prop_when` that uses the condition's name: three tables for
`if(NOT ENABLE_RTTI) -fno-rtti`. Wished for: conditions inline in
`prop_when` (`["cxx.rtti", "off", "!ENABLE_RTTI"]`), or the option name as
an implicit condition. `build_tests` needed
`$And($Eq(option.SPIRV_SKIP_EXECUTABLES, off), $Eq(option.SPIRV_SKIP_TESTS, off))`,
which is hard to read for "not skip-executables and not skip-tests".
Saving: 5 of the 6 condition lines.

**U6. "Build this only when option X" needed an aggregate target in
Datalog** (D3's workaround, 7 lines of `rules.dl`). Wished for, in TOML:
`request_when = [["spirv-as", "!SPIRV_SKIP_EXECUTABLES"]]`.

**U7. Removing a flag from one target: no spelling.** `-Wno-shadow` after
`-Wshadow` doesn't work (sorted set, D5), so I invented
`spvtools_flag_off` (8 rows + a negation in the rule). Wished for:
`prop_remove` or per-target warnings keys.

**U8. Preset sprawl: 11 files, 23 lines.** One-line presets
(`werror.toml`, `skip-tests.toml`, `fuzzer.toml`, `skip-executables.toml`,
`no-color-rtti.toml`), and a typical configure needs four `--user` flags
plus a `-D`:

```
buildlog configure --user $P/apple-clang-arm64.toml --user $P/homebrew-python.toml \
  --user $P/spirv-headers-prefix.toml --user $P/homebrew-googletest.toml \
  -D SPIRV_HEADERS_PREFIX=$SPIRV_HEADERS_PREFIX -C ... project
```

Wished for:
- `-O SPIRV_SKIP_TESTS=on` for options, like CMake's `-D`;
- `--werror` as a flag;
- named preset bundles in one user file (`[preset.mac] include = [...]`);
- `--package-prefix PATH` instead of a preset that only forwards a `-D`
  (`spirv-headers-prefix.toml` is just `package_prefix =
  [["${SPIRV_HEADERS_PREFIX}"]]`).

**U9. Binding Python took a CPS file plus an alias (8 + 2 lines).** The
CPS filename must equal the package name. My first name,
`homebrew-python3.cps`, failed with *package 'Python3' is not named like
its file*, while at the same time *alias has no definition: python3 ->
Python3:Interpreter* and *unresolved dependency: tool python3 ...* were
printed. The last two were consequences of the first, but they came first
in the output. Wished for: `program = { python3 =
"/opt/homebrew/bin/python3" }` in the user file (D4), and consequential
errors suppressed or listed after their cause.

**U10. Confusing errors.**
- *request depends on needed, creating a negation/stratification cycle*
  names neither my rule nor the relation on the path (`config_attr`). It
  took reading core to learn that options reach `needed`. It should name
  the offending rule's file:line and the dependency path.
- *package_data has too many values* (`generators.toml:14`). The row was
  fine; the cause was that `pygen_interpreter`/`dep` in a
  `[target.spirv-tools-tables]` table *above* the top-level arrays made

  error could say "inside [target.spirv-tools-tables]: a top-level
  relation after a table header?".
- Configure errors raise `SystemExit` from `configure_project`, so tests
  have to catch `SystemExit` and scrape stderr instead of reading
  `metrics["errors"]`.

**U11. `why` output.**
- The full proof for one grammar argument is 80 lines, mostly
  configuration bookkeeping (`decl_suffix`, `settings_name`, `holds`,
  `cond_holds`, `relay_cond`). The interesting chain (`package_data` →
  `eff_prop` → `res_pkg_prop` @ `SPIRV-HeadersConfig.cmake:62` →
  `package_prefix` @ preset:4) is buried.
- `--leaves` is readable, but it loses the chain's order, so "why this
  prefix" and "why this include dir" are siblings.
- Import request ids repeat the full path three times per line
  (`import:cmake:/Users/.../SPIRV-HeadersConfig.cmake`), making lines
  250+ characters.
- Wished for: `--flag` accepting a *prefix* (e.g. `--flag
  --spirv-core-grammar=`), since I had to paste the full absolute path,
  and a `--summary` mode that prints only user and package facts with
  file:line, in chain order.

**U12. Test declarations repeat the name.** `test = [["spirv-tools-test_c_interface",
"test_c_interface"], ...]`. Wished for: `test = true` on the target
(named after it) with an optional `test_name`.

**U13. `buildlog test` result lines are fine**, but running a single gtest
filter (`--gtest_filter`) has no pass-through; `buildlog test -R x --
--gtest_filter=Foo.*` would help large suites.

## Linux (GCC 13 and Clang 18)

`linux/run.sh cases gcc|clang spirv-tools` configures, builds (`spirv-opt`, the tools, the
libraries and the googletest programs) and tests (4 ctest tests) on arm64 Ubuntu 24.04.
`linux/run.sh baselines gcc|clang spirv-tools` runs `baseline/run-cmake.sh` in the image
and writes `baseline/linux/` (GCC) and `baseline/linux-clang/` (Clang); the tests pick the
baseline by host (`host.baseline_dir`). All 13 tests pass on Linux with both families,
including the generated tables byte-identical to upstream's, the five generator
commands, the static libraries' flags, and `spirv-tools`' round trip and the C interface
tests.

- **Presets.** `presets/gcc-arm64.toml` and `clang-arm64.toml` (ported from the Apple one),

  is the image's `/opt/spirv-headers` as an installed package, as on macOS.
- **Compiler family.** `-Wno-self-assign`, `-ftemplate-depth=1024` and `-Wextra-semi` are
  upstream's Clang branches; they are `when."cxx.family == clang"` rows (before, the spec
  stated them for Apple clang only), so GCC gets upstream's plain warning set.
- **Timers.** `SPIRV_TIMER_ENABLED` and `source/util/timer.cpp` are `spv_timer`
  (`platform.os == linux & SPIRV_ALLOW_TIMERS`), as upstream's `CMAKE_SYSTEM_NAME` test.
- **Deviations.** Baseline `generators.txt` keeps only the lines that run the interpreter
  (on Linux cmake itself lives under a `python` directory). `build-version.inc` is
  identical to macOS's, since it reads `CHANGES` and git.
- **Not stated:** Android's timers.
